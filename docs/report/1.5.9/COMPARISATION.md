# Audit Reports Comparison

## Purpose

This document compares two independent engineering audits of DOSOUND Tracker produced on 2026-11-12, verifies their findings against the repository tree, and derives an adjustment plan for the audit tooling that produced the weaker report.

The compared reports are `AUDIT-1.6.md`, generated by the lens-skill audit skill on the SWE-2 model, and `ENGINEERING-AUDIT-2026-11-12.md`, generated from an audit prompt on the GPT 6 Sol model.

## Subject Divergence

The two reports audited different commits, one apart in the history.

`AUDIT-1.6` inspected `cef0d425`, the Version 1.5.8 window-close commit.

`ENGINEERING-AUDIT` inspected `eeb20253`, the current HEAD, which reorganized roughly one hundred source and test files into domain directories, added a directory-purity guard test, two refactoring documents, and `AUDIT-1.6` itself.

The divergence explains the unit-test count difference, 1,334 versus 1,335, where the delta is exactly the added directory-purity test.

It also explains most of the format-gate divergence: the nine files that fail `prettier --check .` at `eeb20253` were either added by that commit or carry the deepened import paths its codemod introduced, and they were plausibly clean at `cef0d425`.

The divergence does not explain the deeper finding gaps: the reset-ordering defect, the packaged-license omission, the coverage-floor failure, the license-allowlist violations, and the dev-origin trust issue all live in code that predates the move.

## Methodology Comparison

`AUDIT-1.6` ran a full-tree inventory of roughly 1,215 tracked files, five read-only scouting passes, mechanical censuses for secrets, markers, dead code, licenses, and test placement, a 99-criterion fixed catalogue across 20 dimensions, and a six-command commissioned set inside an isolated copy.

`ENGINEERING-AUDIT` ran a snapshot copy with byte-level comparison to the working tree, targeted source inspection, and a wider executed set covering the typecheck, lint, format-check, build, unit tests, browser smoke, both dependency-advisory scans, a coverage run, an unpacked Electron build, an ASAR content listing, and runtime permission probes.

The decisive methodological difference is the executed surface: the GPT audit exercised every declared project gate, while the lens audit ran only the commands the commissioning prompt named and recorded the rest as not done.

## Verification Results

Verification ran source inspection and git-level checks only.

Executed-check results such as test counts, coverage percentages, and ASAR listings were taken as reported, not re-run.

| Claim group            | AUDIT-1.6      | ENGINEERING-AUDIT   |
| ---------------------- | -------------- | ------------------- |
| File:line citations    | mostly exact   | exact on all checks |
| Census counts          | mostly exact   | exact               |
| Executed-check rows    | one impossible | internally coherent |
| Dependency inventory   | one omission   | exact               |
| Requirements inventory | 33 incl. cases | 27 requirements     |
| Verdict consistency    | inflated       | consistent          |

Confirmed defects inside `AUDIT-1.6`:

- The executed-evidence row records `npm run format:check` exiting zero, but no `format:check` script exists in `package.json` at either commit
- The production-dependency table omits the declared `lucide-react` and lists transitive `yaml` in its place
- Development dependencies are counted as 25 where `package.json` declares 24, and the "30 declared deps" claim is 29
- The "~179 test files" figure conflates all files under `test/` with the ~144 spec files the runner executes
- Non-functional requirements `N-01` and `N-03` are graded Pass on source-plus-suite evidence although glitch-free audio and full DOSOUND compatibility were never measured
- The requirements registry counts the six `C-*` use cases as mandatory requirements, inflating the denominator from 27 to 33
- The READY verdict coexists with material unknowns, an unrun advisory sweep, an unrun coverage floor, and uninspected packaged output
- The Target Environment cell repeats the Node and npm versions twice
- The "~40 hooks" composition-root figure undercounts roughly fifty hook call sites

Minor defects inside `ENGINEERING-AUDIT`:

- The engines entries are described as enforced floors where `package.json` declares `>=` ranges, with the exact pin carried by `.nvmrc`
- The "100% DOSOUND" citation points at the F-07 paragraph, while the literal wording sits in N-03
- Neither report is wrong on the 1,334 versus 1,335 test count, the delta is the subject commit

## Gap Analysis For AUDIT-1.6

The gaps fall into five groups, ordered by impact on the verdict.

**Missing executed-evidence families**

The audit never ran `npm run test:coverage`, `npm audit`, a packaging build, or artifact content inspection, all available in its own environment.

Each was honestly disclaimed as not commissioned, but the disclaimers never reached the verdict.

**Missing finding classes**

The report has no persistence-ordering review, so the reset race escaped detection.

It has no distribution-completeness check, so the missing MIT notice in shipped bundles escaped.

It has no license-policy conformance step beyond the census, so the PSF-2.0 and 0BSD allowlist violations escaped.

**Requirements and grading calibration**

Use-case rows entered the requirements registry, and runtime or hardware-fidelity claims graded Pass without runtime evidence.

**Verdict semantics**

UNKNOWN outcomes reduce coverage but never force a pending-evidence readiness state, so READY survived three material unmeasured gates.

**Evidence-record accuracy**

The report records a script that does not exist and generalizes a check's pass into a whole-tree claim, and the SBOM drops a declared dependency.

## Lens-Skill Adjustment Plan

The plan targets the lens-skill instruction set, not this repository.

Each theme names the owning file and the change that closes the observed gap; implementation is a separate described change under the skill's development mode.

| #   | Theme                          | Primary targets                                                                                                           | Change summary                                                                                                                    |
| --- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Commissioned-evidence defaults | `process/audit-workflow/parameter-phase.md`, `evidence-gathering.md`                                                      | Enumerate the subject's declared check surface and propose it as the commission set instead of a bare free-text ask               |
| 2   | Advisory and coverage prompts  | `process/parameter-configuration.md`                                                                                      | Surface `dependency-advisories` and coverage runs when a lockfile and a coverage gate exist                                       |
| 3   | UNKNOWN and gate semantics     | `process/readiness-scoring.md`, `scripts/check-model.py`                                                                  | Treat unresolved high-criticality criteria as `PENDING EVIDENCE` readiness input for readiness-audit purposes                     |
| 4   | Scoring calibration            | `process/readiness-scoring.md`, `references/criteria-catalogue.json`                                                      | Add an unknown-coverage term or ceiling to the headline score and revisit `TST-GATE` criticality                                  |
| 5   | Registry definition            | `process/audit-workflow/scope-definition.md`, `scripts/extract-requirements.py`, `assessment/requirements-conformance.md` | Exclude use-case and scenario rows from the mandatory registry and record per-row classification                                  |
| 6   | Unverifiable-claim grading     | `assessment/requirements-conformance.md`, `assessment/nfr-review.md`, `references/evidence-schema.md`                     | Grade runtime and compatibility claims Unknown without runtime evidence and add a fidelity claim class                            |
| 7   | Executed-scope reconciliation  | `references/topics/execution-isolation.md`, `process/report-contract.md`, `scripts/validate-report.py`                    | Record each executed command's declared scope, forbid whole-tree claims beyond it, and cross-check verdict vs unresolved criteria |
| 8   | Regression coverage            | `evals/evals.json`, `process/audit-workflow/regression-scenarios.md`                                                      | Add scenarios for commission proposals, scenario-row exclusion, NFR Unknown grading, READY-vs-UNKNOWN, and scope-bounded claims   |

Applying the plan would have changed this audit's outcome mechanically: coverage and advisory runs would have been proposed, the license-policy violations would have surfaced, the packaged artifact would have been inspected, the runtime claims would have graded Unknown, and the verdict would have resolved to pending evidence rather than READY.

## Conclusion

`ENGINEERING-AUDIT` is the stronger verdict instrument: narrower in structure but deeper in executed verification, and its 48% score matches the tree's actual gate state.

`AUDIT-1.6` is the stronger defect inventory: it found ten confirmed code-level issues the other report missed, but its READY verdict and Excellent score are inflated by uncommissioned checks, excluded UNKNOWNs, and an impossible evidence row.

The reports are complementary rather than competing: merging the lens discovery breadth with the gate-execution depth and the calibration discipline of the prompt-run audit would produce the most accurate assessment.

The adjustment plan above closes the specific skill-level causes this comparison identified.
